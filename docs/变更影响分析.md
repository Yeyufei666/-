# 需求变更影响分析（实验二）

> 本文档记录实验二正式需求变更（教师于第 3 周发布的 CR-01 与 CR-02）的影响分析与实施结果。变更在 `baseline-v1` 基础上完成，代码以 `change-v2` 标签封存。

---

## 一、需求变更单 CR-01：新增年级限定报名

### 变更编号与描述

**CR-01**：学校新增仅面向大二、大三学生的活动类别。

- `Activity` 支持"年级限定直接报名"规则（新增报名方式 `grade_direct`）；
- `Student` 新增 `grade` 字段，取值 1~4；
- 仅 `grade ∈ {2, 3}` 的学生可报名此类活动，其他年级收到明确提示；
- 该规则同时遵守名额限制、活动开始时间、重复报名等公共约束；
- 原有"直接报名"和"审核报名"行为不得改变。

### 受影响模块

| 模块 | 影响 |
|------|------|
| models.py | 新增 `PolicyType.GRADE_DIRECT`；`Student` 新增 `grade` 字段；新增 `EmailRecord` |
| policies.py | 新增 `GradeDirectPolicy`；策略接口由 `initial_status()` 扩展为 `decide(student)` |
| services.py | `register()` 改为获取学生对象并调用 `policy.decide(student)` |
| db.py | `student` 表新增 `grade` 列（含轻量迁移）；`email_record` 新表 |

### 设计决策

- **新增独立策略而非改核心流程**：年级限定是"报名资格"差异，与 direct/review 同属"报名规则"变化维度。新增 `GradeDirectPolicy` 子类，`policy_for()` 工厂增加一个分支即可，`register()` 主流程不新增任何 `if` 判断——符合开闭原则（OCP）。
- **年级校验放在策略内部，公共约束留在 Service**：年级资格是策略特有的规则，放进 `GradeDirectPolicy.decide()`；名额、开始时间、重复报名仍是公共约束，由 `RegistrationService` 统一执行。
- **策略接口扩展**：为让策略能基于学生属性做判断，将接口从 `initial_status()` 扩展为 `decide(student)`，接收学生对象。

### 代码差异

| 类型 | 文件 | 说明 |
|------|------|------|
| 新增 | policies.py 内 `GradeDirectPolicy` | 年级限定策略，`ALLOWED_GRADES={2,3}` |
| 修改 | policies.py | 策略接口 `decide(student)`；工厂增加 grade_direct 分支 |
| 修改 | models.py | 新增枚举值 + Student.grade + EmailRecord |
| 修改 | services.py | `register()` 取学生对象并调用 `policy.decide` |
| 修改 | db.py | student 加 grade 列 + 迁移 + email_record 表 |

### 新增/回归测试

| 用例 | 输入 | 期望 | 结果 |
|------|------|------|------|
| CR1-01 | 大二学生报名年级限定 | 通过 | ✅ |
| CR1-02 | 大三学生报名年级限定 | 通过 | ✅ |
| CR1-03 | 大一学生报名年级限定 | 拒绝并显示原因 | ✅ |
| CR1-04 | 大四学生报名年级限定 | 拒绝并显示原因 | ✅ |
| CR1-05 | 变更后重跑 C1~C10 | 全部保持通过 | ✅ |

## 二、需求变更单 CR-02：新增邮件通知

### 变更编号与描述

**CR-02**：管理员希望在站内消息之外，同步向报名学生发送邮件通知。不接入真实邮件服务器，由 `MockEmailSender` 模拟发送，记录收件人、主题、内容、状态与时间。

- 对于"报名通过、审核通过或拒绝"事件，原有站内通知继续运行，同时新增模拟邮件发送；
- 邮件发送故障必须记录错误，但不得错误回滚已成功提交的报名；
- 应避免同一业务事件被重复发送两次。

### 受影响模块

| 模块 | 影响 |
|------|------|
| models.py | 新增 `EmailRecord` 数据类 |
| notifications.py | 新增 `MockEmailSender` 与 `EmailNotificationListener` |
| db.py | 新增 `email_record` 表及读写方法 |
| `__init__.py` | 装配邮件监听器到事件分发器 |

### 设计决策

- **沿用观察者模式**：新增 `EmailNotificationListener` 订阅 `EventDispatcher`，邮件代码不写入 `RegistrationService`，报名/审批主流程零改动。
- **事务边界**：邮件发送失败仅记录错误日志（留痕），不向上抛出，保证不回滚已成功的报名（CR2-03）。
- **避免重复发送**：每个业务动作只发布一次事件，监听器按事件类型（submitted/approved/rejected）消费，取消（cancelled）不触发邮件；重复提交同一动作因"重复报名"约束在源头即被拦截，不会重复产生通知（CR2-04）。

### 代码差异

| 类型 | 文件 | 说明 |
|------|------|------|
| 新增 | notifications.py 内 `MockEmailSender` | 模拟发送，记录到 email_record 表 |
| 新增 | notifications.py 内 `EmailNotificationListener` | 订阅事件发邮件，失败留痕 |
| 修改 | models.py | 新增 EmailRecord |
| 修改 | db.py | email_record 表 + DAO |
| 修改 | `__init__.py` | 注册邮件监听器 |

### 新增/回归测试

| 用例 | 输入 | 期望 | 结果 |
|------|------|------|------|
| CR2-01 | 直接报名通过 | 站内消息和模拟邮件均有记录 | ✅ |
| CR2-02 | 审核批准或拒绝 | 两种渠道记录对应结果 | ✅ |
| CR2-03 | 模拟邮件发送失败 | 报名状态正确、错误有日志 | ✅ |
| CR2-04 | 重复提交同一业务动作 | 不重复生成多份通知 | ✅ |
| CR2-05 | 变更后重跑 C1~C10 | 原有功能保持通过 | ✅ |

## 三、可维护性对照（baseline-v1 vs change-v2）

| 指标 | baseline-v1 | change-v2 |
|------|-------------|-----------|
| 新增类数 | 0（基线） | 2（`GradeDirectPolicy`、`EmailNotificationListener`）+ 1 数据类 + 1 发送器 |
| 修改的核心业务类数 | — | 1（`RegistrationService.register` 仅改为调用 `decide(student)`，主流程逻辑未变） |
| 回归失败数 | — | 0（C1~C10 全部通过） |
| 新增测试用例 | — | 13（CR1×4 + CR2×4 + 边界×5） |
| 修改总时长 | — | 约 1 小时 |

### 反思结论

两个变更恰好分别考验了**策略模式**（新增报名规则）与**观察者模式**（新增通知渠道）的扩展能力：

- **CR-01**：若以"硬编码 if-else"实现，需在 `register` 主流程中插入年级判断分支；采用新增策略后，改动被约束在"新增一个策略子类 + 工厂加一个分支"，`register` 主流程几乎无感。
- **CR-02**：若把邮件代码直接写进 `RegistrationService`，报名事务会与邮件发送耦合；采用新增监听器后，邮件逻辑完全独立，主流程零改动。

模式的收益在真实变更中得到验证；成本仍是抽象层带来的少量类数量增加，但在"需求会变"的前提下是值得的。
