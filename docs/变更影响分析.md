# 需求变更影响分析（实验二）

> 说明：教师将在初版验收后统一发布需求变更单（CR）。本文档预先设计一个**合理且贴近课程目标**的变更方案，用于演示"策略模式 + 观察者模式"应对需求变更的能力；教师发布真实 CR 后，将按真实内容更新本节并在 `change-v2` 标签上实施。

## 预留变更方案（CR-01，示例）

### 变更编号与描述

**CR-01：新增"抽签报名"方式，并支持"邮件通知"渠道**

- 业务规则新增：活动报名方式新增 `lottery`（抽签型）。学生提交报名后进入"待抽签"状态；管理员执行抽签后，中签者"已通过"、未中签者"已拒绝"。
- 通知渠道新增：除站内消息外，抽签结果需额外通过"邮件"通知学生。

> 设计本 CR 的目的：同时考验**策略模式**（新增报名规则）与**观察者模式**（新增通知渠道）的扩展能力，正是实验二"用模式应对变更"的核心考察点。

### 受影响模块

| 模块 | 影响 |
|------|------|
| models.py | 新增 `PolicyType.LOTTERY`、`RegistrationStatus` 可能新增"待抽签"状态 |
| policies.py | 新增 `LotteryPolicy` 实现 `RegistrationPolicy` |
| services.py | `RegistrationService` 新增 `draw()`（抽签）方法；`policy_for()` 工厂增加分支 |
| notifications.py | 新增 `EmailNotificationListener` 监听器，订阅同一事件 |
| db.py | 无表结构变化（状态值扩展即可），或按需新增字段 |

### 设计决策

- **沿用策略模式**：新增 `LotteryPolicy`，主流程 `register()` 与 `policy_for()` 工厂扩展，其余业务逻辑零改动——这正是策略模式收益的体现；
- **沿用观察者模式**：新增 `EmailNotificationListener`，只需 `dispatcher.subscribe()` 即可接入，报名/审批主流程不感知新渠道；
- **无需删除重建**：在 `baseline-v1` 基础上新建分支实现，保留原有全部功能。

### 代码差异（预期）

| 类型 | 文件 | 说明 |
|------|------|------|
| 新增 | policies.py 内 `LotteryPolicy` | 抽签策略实现 |
| 修改 | models.py | 新增枚举值 |
| 修改 | services.py | 新增 `draw()`、扩展工厂 |
| 新增 | notifications.py 内 `EmailNotificationListener` | 邮件通知监听器 |

### 新增/回归测试（预期）

- 新增用例：抽签型活动报名进入"待抽签"；中签/未中签结果正确；邮件通知触发；
- 回归测试：原 C1~C10 全部复测通过，验证新增变更未破坏既有功能。

### 工作量与质量（预期）

- 预计改动 4 个文件、新增 1 个策略类 + 1 个监听器；
- 复用既有测试夹具，回归失败数应为 0。

### 反思结论

本 CR 若以"硬编码 if-else"实现，则需在报名、审批、通知三处主流程中插入新分支，改动面大且易遗漏；采用策略 + 观察者模式后，扩展被约束在"新增策略子类"与"新增监听器"两处，主流程稳定，验证了模式的收益。成本是新增了抽象层，在需求种类很少时会显得"过度设计"。
