## 一、实验目标与需求范围

### 1.1 实验目标

1. 从需求中识别领域对象、业务服务、关系和职责边界，绘制 UML 类图；
2. 理解策略模式、观察者模式与 SOLID 设计原则；
3. 先做设计决策，再指导 AI 按设计完成实现与测试；
4. 面对需求变更，评估影响、修改系统并开展回归测试；
5. 用可测指标评价软件扩展性，而非简单以"用了设计模式"作为结论。

### 1.2 做什么 / 不做什么

- **做**：校园管理员发布活动，学生浏览活动并报名；支持"直接报名"与"管理员审核"两类活动；报名结果通过站内消息通知；提供活动统计。
- **不做**：用户注册、多用户权限系统、邮件/短信推送、复杂日历、移动端 App（指导书明确限定为两类报名规则及两类通知机制的面向对象系统）。

### 1.3 验收依据

以指导书 3.5 节 C1~C10 十个验收用例为初始版本最低验收标准。

## 二、实现方案

### 2.1 环境

- Python 3.11+，Flask + SQLite，pytest；
- 版本控制：Git（baseline-v1 标签封存初始版本）。

### 2.2 系统结构

系统分四层：

1. **模型层（models.py）**：领域对象与状态枚举；
2. **数据访问层（db.py）**：SQLite 持久化封装；
3. **业务层（services.py）**：ActivityService 管活动、RegistrationService 管报名事务；
4. **表现层（views.py + templates）**：Flask REST API 与极简管理界面。

### 2.3 主要模块

| 模块 | 职责 | 运用的设计思想 |
|------|------|----------------|
| RegistrationPolicy | 报名策略抽象 | 策略模式（开闭原则） |
| DirectPolicy / ReviewPolicy | 直接/审核两种策略 | 单一职责 |
| EventDispatcher + 监听器 | 事件分发与站内通知 | 观察者模式（解耦） |
| RegistrationService | 报名事务编排 | 依赖倒置（依赖抽象） |

设计模式与 UML 图详见 `docs/设计文档.md`。

## 五、结果分析（变更影响）

实验二的核心问题是"当需求改变时，为什么仍然需要软件设计和人的判断"。

- **设计的作用**：通过策略模式与观察者模式，把"变化的报名规则"和"变化的通知渠道"隔离到独立抽象之后，使新增规则/渠道只需新增子类/监听器，主流程保持稳定；
- **人的判断**：AI 能生成可用代码，但"名额检查属于公共规则还是策略责任""审核报名是否占用名额"这类语义层面的设计决策，需要人来判断并纠正 AI 的偏差；
- **可测指标**：教师发布的真实 CR-01（年级限定报名）与 CR-02（邮件通知）已实施，变更影响分析见 `docs/变更影响分析.md`。

## 六、问题与反思

### 问题 1：AI 初版对所有活动统一在提交时检查名额

- **现象**：审核型活动名额满时，学生提交审核报名被直接拒绝；
- **原因**：AI 未理解"待审核不占名额"的业务语义，把名额检查放到了通用提交路径；
- **解决**：人工修正——提交时仅直接报名检查名额，批准时统一再次检查；
- **反思**：业务规则中的语义细节是 AI 的薄弱点，必须靠人审查验证。

### 问题 2：通知监听器构造 Message 对象报错

- **现象**：通知写入失败，日志报 `missing message_id`；
- **原因**：dataclass 必填字段未赋初值；
- **解决**：补默认值 0，由数据库自增主键覆盖；
- **反思**：AI 生成的样板代码需配合自动化测试才能在早期暴露问题。

### 尚存局限

- 邮件为模拟发送（MockEmailSender），未接入真实邮件服务器（CR-02 教学要求如此）；
- 权限控制为固定演示账号，未做完整 RBAC；
- 活动删除采用软删除，未实现数据归档清理。
